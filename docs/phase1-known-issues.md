# 第一阶段已知问题清单

## 需要现场验证

- 手机摄像头扫码兼容性需要在学校实际手机、浏览器和网络环境中验证。
- 正式网页扫码必须使用 HTTPS；本地 `localhost` 可用于开发验证。
- 微信小程序版本应改用微信原生扫码能力，复用当前后端考勤接口。

## 部署环境硬性依赖

- 排课求解器 OR-Tools CP-SAT 是生产必装依赖：`pip install -r server/solver/requirements.txt`，并用 `SCHEDULER_PYTHON` 指向对应 Python。未安装时系统自动回退内置启发式算法，小年级可用，但全校规模会出现课程排不满（16 班高中场景实测缺排 133 节），`test:phase1` 与 `test:benchmark` 也依赖该环境。
- 可通过 `/api/health` 的 `schedulingSolver` 字段、readiness 的 `scheduling_solver` 检查项以及行政排课预检面板确认求解器状态。

## 当前试运行限制

- 排课高级能力仍放在后续迭代，包括老师不可用时间、偏好、连堂课、专用教室、合班/走班/分层教学、拖拽调整、多版本回滚和调课审批。
- 第一阶段薪资规则聚焦任课老师：固定工资、岗位工资、正常课时、早自习、晚自习、周末课、补课和个税试算。
- 财务锁定工资前，系统会阻止仍存在待处理或异常课时的老师进入锁定。
- 当前使用本地 JSON 文件作为试运行数据存储，正式上线前需要切换到数据库迁移方案。
- JSON 存储层已做写合并、原子写、会话索引和热路径缓存，实测支撑 3000 人同时在线的读为主负载（稳态约 450 req/s，P99 ≤ 131ms，见 `scripts/load-test.js`）。它的边界是：单进程、全量序列化落盘（每次写盘约 30~40ms 且随数据量线性增长）、无跨进程事务。当课次/考勤流水累计到约 10 万条以上，或需要多实例部署时，必须按 `docs/database-migration-plan.md` 切换 PostgreSQL。

## 第二阶段（人事管控）注意事项

- `HR_ENCRYPTION_KEY` 是人事敏感字段的生命线：丢失密钥则已加密的证件/银行卡永久无法解密，生产密钥必须离线备份两份以上。
- 学部负责人的审批范围按 `scopeStageIds` 判定，非教学部门（行政后勤等）的流程步骤由人事专员或总校代理处理。
- 入职终审通过即建档开号；非教师序列岗位本期只建档案不开登录账号（其业务功能在第三阶段交付）。
- 离职生效会自动取消生效日后的已发布课次；被取消课次需要行政重新排课发布，系统会推送提醒。
- 审批超时提醒依赖服务进程内的小时级扫描任务，多实例部署时应只在一个实例上启用（当前单实例无此问题）。

## 运营注意事项

- 老师默认密码上线前必须要求修改，管理员可重置密码或停用账号。
- 教室大屏密钥应由总校或信息管理员统一管理，不能贴在公开文档里。
- 薪资规则调整后，已锁定工资不应被重新生成；未锁定数据可重新生成。
