## 1. 阶段定位与总体策略

### 1.1 定位

本阶段是**纯体验阶段**：不新增任何业务能力，把系统的交互质感从"功能完整的 Web 系统"推到"对标 Lark 的成品软件"。它在三个业务阶段全部交付之后进行，原因有二：

1. **打磨的输入是真实使用反馈**。一、二、三阶段上线后积累的用户抱怨、高频操作路径、真实卡点，才是打磨优先级的依据——没有这些数据，打磨就是自嗨。
2. **体验工作的边际价值低于业务闭环**。在全员工资没跑通之前投入动画和手势，是错误的资源分配。

### 1.2 与前序体验工作的关系（避免重复）

2026-07 已完成的 P0/P1 交互升级（不在本阶段范围内）：

| 已交付 | 内容 |
| --- | --- |
| 弹层体系 P0-A | openDialog/confirmDialog/promptDialog，替换全站 20 处原生弹窗，移动端 sheet |
| 操作反馈 P0-B | 骨架屏（HR/财务列表）、常驻错误态+重试、按钮 loading |
| 全局搜索 P1-A | ⌘K 命令面板：功能页 + 人员搜索、键盘导航 |
| 实时推送 P1-B | SSE：审批/通知即时更新、待办角标、断线重连 |

本阶段做的是当时明确**暂缓**的 P2 项与深水区项。

### 1.3 总体策略

- **反馈驱动**：入场时先跑一轮「体验反馈收集」（见 6.1），用真实数据重排本 PRD 内批次的优先级；PRD 给出的排序是默认值，不是铁律。
- **小批次可中断**：每个批次（4A~4F）独立上线、独立回滚（前端改动靠缓存版本号一键回退），任何时刻被业务需求打断都不留半成品。
- **不动业务逻辑红线**：本阶段任何改动不得触碰排课/薪资/审批的领域层代码；涉及接口只允许"新增只读接口/推送主题"，禁止修改既有接口语义。

## 2. 批次范围详述

### 4A 反馈深度：乐观更新与撤销（FB）

解决"每次操作都要等全页刷新"的迟滞感。

- FB-1 乐观更新：高频轻量操作（通知已读、待办勾选、筛选切换、确认工资）点击后 UI 立即变化，请求失败自动回滚并提示。范围白名单制，逐个操作评审后纳入——**任何涉及金额与审批状态跃迁的操作不做乐观更新**。
- FB-2 可撤销操作：非终态的删除/归档类动作（如撤回审批、删除草稿学期）执行后 toast 提供 5 秒「撤销」；超时才真正提交。终态动作（锁定工资、离职生效）明确不做撤销，维持现有二次确认。
- FB-3 骨架屏全覆盖：把 P0-B 只覆盖 3 个列表的骨架屏推广到全部异步列表（通知、审计、工资记录、课表加载）。
- FB-4 按钮 loading 全覆盖：所有写操作按钮统一接入 loading 态（P0 只覆盖了弹层内按钮）。

### 4B 动效与弹层扩展（MOTION）

解决全量重渲染带来的"生硬感"，但不重写渲染架构。

- MO-1 关键过渡动画：视图切换淡入、列表行进出位移、面板展开收起，全部用 CSS transition/animation 实现（无 JS 动画库）；遵守 `prefers-reduced-motion`。
- MO-2 局部渲染止血：对 3 个重渲染热点（通知列表、审批列表、财务教师列表）做增量 DOM 更新，消除刷新闪烁与滚动跳动。**明确不引入前端框架**——如评估后认为必须框架化，单独立项报批，不在本阶段内。
- MO-3 右侧抽屉 Drawer：档案详情、审批详情、工资单详情改为右侧滑出抽屉（桌面端），列表上下文不丢失；移动端保持全屏。
- MO-4 悬停微交互：人员姓名 hover 出信息卡（部门/岗位/状态）、图标按钮 tooltip 统一。

### 4C 搜索与键盘效率（SEARCH）

- SE-1 命令面板扩展：搜索范围从"功能页+人员"扩展到审批单（按工号/姓名/类型）、通知、以及**动作命令**（"生成本月工资""发起入职"等直接执行入口，带权限过滤）。
- SE-2 最近访问：命令面板空态显示最近打开的页面与人员，替代静态提示。
- SE-3 快捷键体系：`?` 唤起快捷键速查；`g+字母` 页面跳转；列表 `j/k` 移动、`Enter` 打开；弹层/抽屉 Esc 统一关闭（已有）。全部快捷键在输入框聚焦时自动失效。
- SE-4 表格增强：列表头点击排序、表头吸顶全覆盖、长列表虚拟滚动评估（仅审计页等千行级列表）。

### 4D 移动端原生感与 PWA（MOBILE）

第三阶段 3A 全员移动考勤上线后，移动端从"教师查看为主"变成"全员每日打卡"，是打磨收益最大的端。

- MB-1 下拉刷新：列表页支持下拉刷新（替代找刷新按钮）。
- MB-2 底部操作单：移动端行内操作（审批通过/拒绝、状态变更）从小按钮改为点行弹出底部 action sheet。
- MB-3 PWA：manifest + service worker 壳缓存，支持"添加到主屏幕"全屏运行；离线时展示明确的离线态（不做离线数据，打卡等写操作必须在线）。
- MB-4 触感细节：点击涟漪/按压态、safe-area 适配复查、输入框聚焦不被键盘遮挡。

### 4E 实时协同扩展（LIVE）

在 P1-B SSE 基座上扩展主题与规模。

- LV-1 推送主题扩展：排课任务完成、工资发布、OA 审批结果（三阶段产物）接入 SSE，消除这些场景的手动刷新。
- LV-2 编辑互斥提示：排课草稿、薪资配置等单资源编辑页，第二人进入时提示"××正在编辑"（提示不锁死，冲突仍由后端版本校验兜底）。
- LV-3 多实例广播：SSE 广播接 Redis pub/sub，解除单实例限制（与运维手册多实例前置项合并执行；若届时仍单实例部署，本项降级为文档确认）。

### 4F 空态、引导与可访问性（POLISH）

- PO-1 空态升级：全部空态从一行灰字升级为"插画（轻量 SVG）+ 一句话说明 + 行动按钮"。
- PO-2 新手引导：每个角色首次登录展示 3~4 步功能指引（可跳过、可重看）；配套简版帮助页替代散落的 tips。
- PO-3 可访问性基线：焦点可见性全覆盖、弹层/抽屉焦点圈闭（focus trap）、关键流程 aria 标注、对比度按 WCAG AA 复查。
- PO-4 一致性终审：日期/金额/状态文案、按钮位置（主按钮右置）、危险色使用，全站走查一遍并修偏差。

## 3. 明确不做（本阶段红线）

| 项 | 原因 |
| --- | --- |
| 前端框架重写（React/Vue 化） | 投入巨大且回归风险不可控；MO-2 局部增量更新已覆盖主要痛点。如确需，单独立项 |
| 拖拽调课 | 交互收益高但涉及排课领域逻辑与冲突校验联动，违反"不动业务逻辑"红线；作为独立业务需求评估 |
| 深色模式 | 学校办公场景需求弱，维护成本（全站双主题回归）不成比例 |
| 原生 App | PWA（MB-3）已覆盖"图标进桌面、全屏体验"诉求 |
| 离线数据同步 | 打卡/审批必须在线才有效力，离线缓存业务数据引入一致性风险 |

## 4. 优先级与排期（默认值，入场反馈可重排）

| 批次 | 主题 | 默认优先级 | 预估 | 依赖 |
| --- | --- | --- | --- | --- |
| 4A | 反馈深度 | P0 | 1 周 | 无 |
| 4D | 移动端与 PWA | P0 | 1.5 周 | 3A 全员考勤已上线 |
| 4B | 动效与抽屉 | P1 | 1.5 周 | 无 |
| 4C | 搜索与快捷键 | P1 | 1 周 | 无 |
| 4F | 空态引导与可访问性 | P1 | 1 周 | 建议最后（终审性质） |
| 4E | 实时协同扩展 | P2 | 0.5~1 周 | 三阶段推送场景就绪；LV-3 依赖多实例决策 |

排序依据：4A/4D 直接作用于全员每日高频动作（打卡、审批、确认工资），收益最大；4F 放最后是因为它包含全站一致性终审，宜在其它批次改完后收口。

## 5. 验收标准

1. **零业务回归**：`npm run check` + 全部既有测试套件通过；每批次上线前后各跑一次。
2. **性能预算**：首屏可交互 ≤ 2s（校内网络）；任何动画不引发布局抖动（CLS≈0）；app.js 体积增幅 ≤ 15%。
3. 4A：白名单内操作点击到 UI 反馈 ≤ 100ms；失败回滚可演示；撤销窗口内不产生后端写入。
4. 4B：三个热点列表刷新不再整页闪烁（录屏对比）；`prefers-reduced-motion` 下动画全部停用。
5. 4C：命令面板可搜到审批单并直达；快捷键速查页完整；输入框聚焦时快捷键零误触。
6. 4D：主流机型（iOS Safari / Android Chrome）添加到主屏后全屏运行；下拉刷新与 action sheet 在真机验证。
7. 4E：新增主题推送端到端演示；双人编辑互斥提示可复现。
8. 4F：axe 或同级工具扫描无严重级问题；每个角色新手引导可完整走完。
9. **真实用户抽验**：每批次上线后抽 3~5 名真实用户（覆盖老师/行政/财务/人事）口头回访，记录进验收单。

## 6. 入场条件与工作方式

### 6.1 入场条件（缺一不启动）

- [ ] 第三阶段 3E 验收通过，系统全量在生产稳定运行 ≥ 2 周。
- [ ] 完成一轮体验反馈收集：各角色 ≥ 3 人访谈 + 高频操作路径统计（可用审计/日志粗算），产出《体验反馈清单》。
- [ ] 用反馈清单校准本 PRD 批次优先级，确认后冻结本轮范围。
- [ ] 无 P0/P1 级业务缺陷在修。

### 6.2 工作方式

- 每批次：改动 → 全套件回归 → 三视口浏览器走查 → 缓存版本号升级 → 上线 → 真实用户抽验 → 记 CHANGELOG。
- 任何批次可被业务需求打断；打断时当前批次要么完整上线要么整体回退，不留中间态。
- 回滚手段：前端批次靠缓存版本号回退 + git revert；4E 后端改动按部署手册第 7 节执行。
