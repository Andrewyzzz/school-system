## 1. 项目背景与目标

### 1.1 阶段定位

第一阶段已交付「任课教师排课 → 扫码考勤 → 工作量确认 → 薪资核算 → 财务锁定」闭环，并完成生产化加固（跨年级全局冲突校验、学期生命周期隔离、3000 并发验证、OR-Tools 生产依赖显性化）。但目前"人"的入口是失控的：教师档案靠 CSV 导入和种子数据，没有入职审批、没有调岗离职流程、没有岗位与薪资模板的绑定。

第二阶段的唯一主题：**管住人的全生命周期**。让系统回答并控制四个问题：

1. 谁可以进入系统（入职审批）；
2. 谁现在处于什么岗位、什么状态（在职档案）；
3. 谁的状态变化如何影响排课与计薪（调岗、离职、停用联动）；
4. 谁能看到和操作什么数据（分级权限）。

### 1.2 业务价值

- 堵住三类真实风险：**私自用人**（未审批先上课）、**挂名吃薪**（不在岗仍计薪）、**离职后发薪**（状态不同步）。
- 每一次人事变动留痕可审计，为劳资纠纷提供系统证据。
- 岗位与薪资模板绑定后，financeg工资档案不再逐人手工维护，为第三阶段全员薪资打底。

### 1.3 入场条件（工程前置，硬性）

| 前置项 | 说明 | 截止 |
| --- | --- | --- |
| PostgreSQL 迁移 | 人事档案含身份证、银行卡、合同等敏感信息，且审批流写入频繁；JSON 文件层已明确边界（约 10 万流水、单实例）。第二阶段开发必须在 SQL 数据层上进行，schema 已有初版（`database/postgres/001_phase1_schema.sql`） | M1 结束前完成读写切换 |
| 生产 HTTPS/域名闭环 | 一阶段遗留项，涉及扫码与登录安全 | 试运行前 |
| 第一阶段试运行验收通过 | 人事联动逻辑以一阶段口径为基线 | 2026-07-15 |

## 2. 范围定义

### 2.1 必须交付（验收强制项）

1. 学校组织架构管理：总校 → 学部（幼儿园/小学/初中/高中/行政后勤/财务/招生/安保）→ 部门/年级组，支持启停和调整留痕。
2. 人员档案全量字段：基本信息、证件、部门岗位、入职日期、合同（起止、类型、签订记录）、薪资模板引用、状态机。
3. 入职审批流：学部发起 → 总校审批 → 自动开通账号与档案；拒绝有原因留痕。
4. 状态机与联动：`待入职 → 试用期 → 在职 → 调岗中 → 离职中 → 已离职 / 停用`；状态变化自动联动账号可用性、排课任课池资格、计薪资格。
5. 调岗流程：跨部门/跨学部调岗审批，生效日期控制课时归属和薪资模板切换。
6. 离职流程：发起 → 审批 → 交接确认（课表移交提示）→ 生效；生效后账号停用、退出任课池、当月计薪截止到生效日。
7. 岗位与薪资模板：岗位字典（教师类岗位先行）与薪资模板绑定，新入职按岗位自动带出工资档案默认值。
8. 分级权限：新增「学部负责人」角色（只见本学部人员与审批）、「人事专员」角色（全校档案管理，无薪资金额查看权）；权限矩阵见 3.2。
9. 人事操作全量审计：谁、何时、对谁、改了什么（前值/后值）、为什么。
10. 未审批人员、离职人员、停用人员**不能**出现在排课任课池、不能被生成工资。

### 2.2 明确不做（留给第三阶段）

- 非教师岗位的工资方案计算（档案可以录入，薪资模板仅教师类生效）。
- 请假、加班、报销等 OA 审批。
- 移动端打卡。
- 招聘管理（简历、面试）。
- 电子合同签署（仅记录合同元数据与线下扫描件附件路径）。

### 2.3 关键假设与依赖

- 学校在 M1 前提供：正式组织架构表、岗位清单、各岗位薪资模板初值、存量人员花名册（含在职状态）。
- 审批链先固定为两级（学部 → 总校），不做可配置审批流引擎；引擎化留给第三阶段 OA（本阶段的审批数据结构需为其预留 `flowType`、`stepIndex` 字段）。
- 存量 1000 名教师档案通过一次性迁移脚本导入，默认状态「在职」，不补溯历史审批。

## 4. 核心业务流程

### 4.1 入职（主链路）

> 学部负责人发起（岗位+拟入职日期+基本信息）→ 人事专员补全档案与合同 → 总校管理员审批 → 系统自动：建档案（状态=试用期或在职）+ 建账号（默认密码策略）+ 按岗位模板生成工资档案 → 通知学部与本人 → 教师类岗位自动进入对应学部任课池。

拒绝路径：任一环节拒绝 → 状态=已拒绝，原因必填，可重新发起（新流水号）。

### 4.2 调岗

> 发起（目标部门/岗位+生效日期+原因）→ 原学部负责人确认 → 目标学部负责人确认 → 总校审批 → 生效日零点起：档案部门岗位切换、薪资模板按新岗位切换（当月工资按生效日分段归属，见 4.5）、任课池从原学部移除并加入新学部。

排课联动：调岗生效前，若该教师在原学部有生效日之后的已发布课表，系统在审批通过时生成「课表移交提醒」清单推送给原学部行政，行政必须处理（调课/换师）后调岗才最终生效（可由总校强制生效并留痕）。

### 4.3 离职

> 发起（拟离职日期+原因分类）→ 学部负责人确认 → 总校审批 → 交接检查（系统自动列出：生效日后的已发布课表、未确认工作量、未锁定工资）→ 生效：账号停用、退出任课池、档案状态=已离职。

计薪规则：离职当月工资 = 生效日（含）前的有效课时 + 固定项按 `在职天数/当月天数` 折算（折算规则须学校在 M2 前书面确认，默认按自然日折算）；离职后该教师工资单仍可由财务查看与导出，不可再生成新月份。

### 4.4 停用（非流程性风控开关）

总校管理员或系统管理员可即时停用账号（如安全事件），停用≠离职：档案保留在职状态，任课池冻结，登录拒绝；恢复需总校确认。所有停用/恢复留痕。

### 4.5 人事状态 × 一阶段业务联动矩阵（生产关键）

| 状态 | 能否登录 | 出现在任课池 | 已发布课表 | 可否签到 | 当月计薪 |
| --- | --- | --- | --- | --- | --- |
| 待入职 | 否 | 否 | — | 否 | 否 |
| 试用期 | 是 | 是 | 正常 | 是 | 按模板试用系数 |
| 在职 | 是 | 是 | 正常 | 是 | 正常 |
| 调岗中（未生效） | 是 | 原学部 | 正常 | 是 | 原模板 |
| 离职中（未生效） | 是 | 冻结新增 | 保留，提示移交 | 是 | 正常至生效日 |
| 已离职 | 否 | 否 | 生效日后课次自动取消并提醒行政 | 否 | 截止生效日 |
| 停用 | 否 | 冻结 | 保留 | 否 | 冻结（需人工裁定） |

## 5. 功能需求详述（模块编号）

### 5.1 组织架构（ORG）

- ORG-1 树形架构维护：增改停用节点，节点类型（学部/部门/年级组），停用节点下有在职人员时拦截。
- ORG-2 架构调整留痕：任何节点变更记录操作人、时间、原因。
- ORG-3 与排课学部映射：教学类学部节点与一阶段 `stageId/divisionId` 建立映射表，不改动一阶段排课模型。

### 5.2 人员档案（EMP）

- EMP-1 档案字段全集：身份（姓名、证件类型号码、出生、性别、联系方式、紧急联系人）、组织（部门、岗位、汇报对象）、雇佣（入职日、转正日、合同列表、社保参缴状态标记）、教学（学部、学科、职称——沿用一阶段字段）、薪资模板引用。
- EMP-2 敏感字段脱敏展示：证件号、银行卡默认掩码，查看完整值需二次确认并留审计。
- EMP-3 档案变更申请：老师本人可发起联系方式等非关键字段修正，人事专员审核生效。
- EMP-4 存量迁移：一阶段 1000 教师档案一次性迁移脚本 + 迁移核对报告（数量、字段完整率）。
- EMP-5 花名册导出：按权限范围导出 CSV（不含敏感明文），导出动作留审计。

### 5.3 审批流（FLOW）

- FLOW-1 三类流程实例：入职、调岗、离职；统一数据结构（flowType、当前步骤、每步操作人/时间/意见/附件）。
- FLOW-2 待办列表：各角色首页显示待我审批数量与列表，支持通过/拒绝+意见。
- FLOW-3 超时提醒：审批停留超 3 个工作日，通知中心提醒审批人与发起人。
- FLOW-4 撤回：发起人在下一步未处理前可撤回。
- FLOW-5 为第三阶段预留：步骤定义表驱动（本阶段写死两级链，但数据结构支持 N 步）。

### 5.4 岗位与薪资模板（TPL）

- TPL-1 岗位字典：岗位编码、名称、所属序列（教师/行政/后勤/…）、启停。
- TPL-2 模板绑定：教师类岗位绑定一阶段工资档案默认值（职称档、考核档、住房档、津贴项默认集合）。
- TPL-3 模板版本化：模板修改产生新版本，仅影响之后入职/调岗者，存量档案不自动变更（可批量应用并留痕）。
- TPL-4 非教师岗位模板：仅存字段结构，金额计算第三阶段生效。

### 5.5 权限与账号（PERM）

- PERM-1 新角色接入现有 token/会话体系；一账号一主角色，学部负责人带 `scopeStageIds`。
- PERM-2 数据范围过滤中间件：按角色 scope 过滤档案/审批/审计查询。
- PERM-3 账号生命周期由人事状态驱动（见 4.5），系统管理员保留技术性直接停用通道。

### 5.6 审计（AUD）

- AUD-1 人事域审计独立存储：操作类型、目标人、字段级 diff（前值/后值）、原因、IP/UA。
- AUD-2 审计查询：按人、按操作人、按时间范围；只读，任何角色不可删改。
- AUD-3 敏感读取审计：完整证件号查看、花名册导出计入。

## 6. 数据模型（新增实体）

| 实体 | 说明 | 关键字段 |
| --- | --- | --- |
| org_units | 组织节点 | id, parentId, type, name, stageIdMapping, status |
| employees | 人员档案（教师档案扩展为全员档案，teacher 表保留教学字段并外键关联） | id, personName, idCardEncrypted, orgUnitId, positionId, status, hiredAt, regularizedAt, leftAt |
| employee_contracts | 合同 | employeeId, type, startDate, endDate, signedAt, fileRef |
| positions | 岗位字典 | id, code, name, series, status |
| salary_templates / versions | 薪资模板与版本 | positionId, version, payload(JSON), effectiveFrom |
| hr_flows / hr_flow_steps | 审批流实例与步骤 | flowType, employeeId, status, stepIndex, actorId, action, comment, actedAt |
| hr_audit_logs | 人事审计 | actorId, targetEmployeeId, action, fieldDiffs(JSON), reason, createdAt |

存储要求：`idCardEncrypted`、银行卡号采用应用层加密（AES-256-GCM，密钥走环境变量/KMS），数据库与备份中不落明文；所有新表带 `created_at/updated_at`，高频查询按 orgUnitId、status、employeeId 建索引。

## 7. 接口清单（规划）

- 组织：`GET/POST /api/org/units`、`POST /api/org/units/:id/status`
- 档案：`GET /api/employees`（分页+scope 过滤）、`GET/PATCH /api/employees/:id`、`POST /api/employees/:id/sensitive-view`（二次确认读取）、`GET /api/employees/export`
- 流程：`POST /api/hr-flows`（type=onboard/transfer/offboard）、`GET /api/hr-flows?todo=1`、`POST /api/hr-flows/:id/steps/:index/approve|reject|withdraw`
- 模板：`GET/POST /api/positions`、`GET/POST /api/salary-templates`、`POST /api/salary-templates/:id/apply-batch`
- 联动（内部）：人事状态变更事件 → 账号服务、任课池过滤、计薪资格判定
- 审计：`GET /api/hr-audit-logs`

一阶段接口改造点：`/api/scheduling/config` 任课老师池增加人事状态过滤；`/api/payroll/*` 生成前校验计薪资格；登录校验读人事状态。

## 8. 非功能需求

### 8.1 性能与规模

- 全员规模按 1500 人（教师 1000 + 其他岗位 500）设计；档案列表分页 P95 < 300ms。
- 审批操作写路径 P95 < 500ms；并发基准沿用一阶段 3000 在线压测框架，新增人事接口场景。

### 8.2 安全与合规（人事数据为最高敏感级）

- PII 加密存储（见 6）；传输强制 HTTPS。
- 权限默认拒绝：新接口一律显式声明允许角色，scope 过滤在服务层强制。
- 审计不可篡改：hr_audit_logs 仅追加；数据库账号区分应用读写/只读运营。
- 备份加密：包含人事库的备份文件加密存储，保留 90 天；每月演练恢复一次并记录。
- 离职数据保留：档案与审计按劳动法争议时效保留（建议 ≥3 年），不做物理删除，提供"封存"视图。

### 8.3 可运维性

- 人事状态联动全部通过领域事件函数收口（单一入口），禁止散落 if 判断，保证行为可测试。
- readiness 增加第二阶段检查组：SQL 连接、加密密钥可用、审批超时扫描任务存活。

## 9. 验收标准

1. 组织架构可维护，节点停用拦截规则生效。
2. 走通完整入职：发起 → 审批 → 自动建档建账号 → 新账号登录 → 出现在任课池。
3. 走通调岗：跨学部调岗后，原学部任课池移除、新学部出现、课表移交清单生成。
4. 走通离职：生效后登录被拒、任课池移除、生效日后课次取消提醒、当月工资截止生效日。
5. 未审批完成的人员无法被排课、无法生成工资（自动验收脚本断言）。
6. 学部负责人只能看到本学部数据（越权访问自动验收断言 403）。
7. 敏感字段掩码与完整读取审计生效。
8. 全部人事写操作可在审计中查到字段级 diff。
9. 存量 1000 教师档案迁移核对报告 100% 通过。
10. PostgreSQL 数据层：一阶段全部既有测试（phase1/cross-grade/term-lifecycle/scheduling-jobs）在 SQL 层通过。
