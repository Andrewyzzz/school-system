# 技术架构与安全审计说明

> 编写日期：2026-08-08
> 审计方式：**逐条实际发起请求验证**，非代码走读推断。文中所有"已拦截/未拦截"的结论均可复现。
> 适用版本：当前 main 分支

---

## 一、技术架构

### 1.1 总体选型：零框架

生产依赖只有一个 `pg`（PostgreSQL 驱动）。没有 Express、React、Vue，没有打包工具。

| 层 | 实现 | 说明 |
| --- | --- | --- |
| 前端 | 原生 JS 单文件 + HTML + CSS | 无构建步骤，浏览器直开 |
| 服务端 | Node.js 原生 `http.createServer` | 手写路由分发 |
| 持久层 | PostgreSQL，文档式表 | `app_<集合名>`(id, seq, data JSONB) |
| 求解器 | Python + Google OR-Tools | 唯一的外部运行时依赖 |
| 实时推送 | SSE（Server-Sent Events） | 非 WebSocket，单向推送足够 |
| 测试 | Node 内置 `assert` | 12 个套件，无测试框架 |

**这样选型的理由**：学校环境的运维能力有限，依赖越少越不容易坏。没有 npm 依赖链就没有供应链风险，没有构建步骤就不会出现"本地能跑线上白屏"。

**代价（明确的技术债）**：前端 `app.js` 16,824 行单文件，后期维护和多人协作成本高。第四阶段有模块化计划。

### 1.3 数据存储设计

采用**文档式表**而非传统关系建模：每个集合一张表，结构为 `(id TEXT PK, seq BIGINT, data JSONB, updated_at)`。

- 好处：业务字段增删不需要 DDL 迁移，`data` 里加字段即可
- 代价：无法用外键约束保证引用完整性，需在应用层校验

`DB_DRIVER` 环境变量可切换 `json` / `dual` / `postgres` 三种模式，`dual` 用于迁移期双写核对。

**重复主键守卫**：持久化前检查每个集合的 id 唯一性，发现重复**拒绝整批写入**并报错，而不是让后写的覆盖先写的。这个机制在开发期抓到过多次跨学期主键冲突。

## 二、排课算法

### 2.1 主算法：CP-SAT 约束求解

使用 Google OR-Tools 的 CP-SAT 求解器（`server/solver/ortools_scheduler.py`）。**是精确约束求解，不是遗传算法或模拟退火。**

**建模方式**：为每个「课程任务 × 可授课教师 × 可用时段」创建一个布尔变量 `x[task][teacher][date][period]`，表示"该任务是否安排在此教师此时段"。

**硬约束**（必须满足，违反则无解）：

| 约束 | 模型表达 |
| --- | --- |
| 每个课程任务恰好排一次 | `sum(task_vars) == 1` |
| 同一教师同时段至多一节 | `sum(vars) <= 1` |
| 同一班级同时段至多一节 | `sum(vars) <= 1` |
| 同一教室同时段至多一节 | `sum(vars) <= 1` |
| 每班每科每日课时上限 | `sum(vars) + locked <= max_per_class_per_day` |
| 每班每科每日课时下限 | `sum(vars) + locked >= min_per_class_per_day` |
| 每科每周最少上课天数 | 引入 `day_has_subject` 指示变量后求和约束 |
| 教师每日课量上限 | `load + fixed_day_load <= max_daily_lessons` |
| 同班连堂上限 | 滑动窗口内 `sum(vars) + fixed <= max_consecutive` |
| 教师连堂上限 | 同上 |

**软约束**（写入目标函数，`Minimize` 加权惩罚）：课程在周内的分散度、教师日负载均衡、超出日课量上限的部分。

### 2.2 回退与可用性

OR-Tools 不可用时降级到 JS 启发式排课，但会显式报错「OR-Tools CP-SAT 求解器不可用」，不静默降级。

- 生产环境**必须**安装：`pip install -r server/solver/requirements.txt`
- `SCHEDULER_PYTHON` 环境变量可指定 Python 解释器路径
- 服务启动时预热探测，结果长缓存，避免每次请求都探测（探测本身约 1-2 秒）

### 2.3 执行方式

排课任务在 Worker 线程异步执行，前端轮询进度，不阻塞 HTTP 请求处理。实测一个年级（10 个班）约 8-20 秒。

## 三、安全审计

### 3.1 已验证能拦截的攻击

**以下每一条都实际发起了请求，下方是真实返回。**

| # | 攻击场景 | 系统响应 |
| --- | --- | --- |
| 1 | 不带 token 读工资单 | `请先登录` |
| 2 | 伪造 token（`Bearer deadbeef`） | `请先登录` |
| 3 | 老师账号读他人工资 | `只能访问本人教师数据` |
| 4 | 老师账号改自己的工资档案 | `只有财务或行政管理可以维护教师工资档案` |
| 5 | 老师账号改全校薪资标准 | `当前账号无权访问该资源` |
| 6 | 小学部财务查初中部老师工资 | `只能处理小学部的薪资数据` |
| 7 | 小学部财务批量锁定初中部老师工资 | HTTP 403 |
| 8 | SQL 注入 `' OR 1=1--`（搜索框） | 返回 0 条，注入未生效 |
| 9 | 财务重新生成已锁定的工资单 | `本月薪资已锁定，不能重新生成` |
| 10 | 暴力撞库 | 第 11 次返回 429 锁定 |

### 3.2 安全机制

**身份认证**

- 密码：PBKDF2-SHA256，8 万轮迭代，每账号独立随机盐（16 字节）
- 比对：`crypto.timingSafeEqual`，防时序侧信道
- 登录热路径用异步版本（`pbkdf2` 而非 `pbkdf2Sync`），避免 8 万轮计算独占事件循环拖慢全站
- Token：32 字节密码学随机数，**数据库只存 SHA-256 哈希**，不存明文；有效期 12 小时

**防撞库**（实测有效）

- 按用户名：60 秒内失败 10 次锁定该账号
- 按 IP：60 秒内 3000 次限流（**见下方风险 3，此阈值形同虚设**）

**敏感信息保护**

- 身份证号、银行卡号：AES-256-GCM 加密存储，每条独立 12 字节 IV
- 密钥来自环境变量 `HR_ENCRYPTION_KEY`（32 字节），开发用 `.hr-dev-key` 且已 gitignore
- **密钥缺失或格式错误时拒绝写入**敏感字段，而不是降级为明文落库
- 列表接口返回掩码值，明文需单独调用揭示接口并记录审计

**SQL 注入防护**

- 所有值参数走 `$1, $2` 占位符
- 表名虽是字符串拼接（文档式表设计所致），但经过 `/^[a-zA-Z][a-zA-Z0-9_]*$/` 白名单校验，非法集合名直接抛错拒绝建表

**权限模型**

- 角色：teacher / admin(教研所) / finance / hr / division_head / system_admin / classroom
- 财务四分权：三个学部财务各管本部任课老师，总校财务管行政后勤
- 越权拦截放在路由**唯一入口**，读写一并管住，不依赖前端隐藏
- 职责分离：人事管事实（职称、学历、校龄、兼岗任命），财务管金额（考核档、住房档、奖扣），互相改不了对方的字段

**审计留痕**

- 当前 12,111 条审计日志，覆盖登录登出、排课发布、工资生成/发布/锁定、教师导入、任课配置变更等
- 人事域有独立的 `hrAuditLogs`，敏感字段揭示操作单独记录

**业务层防篡改**

- 工资单锁定后不可重新生成、不可修改
- 修改薪资标准会自动作废未锁定的工资单（强制重算），**已锁定的不受影响**
- 学期归档后该学期数据只读

### 3.3 五个真实风险（上线前必须处理前两项）

**风险 1 · 没有 HTTPS（严重）**

服务是 `http.createServer`，全程明文传输。同网段抓包即可获取登录 token 和全部工资数据，也可实施中间人攻击。

> 处置：上线前必须在前面挂 Nginx / Caddy 做 TLS 终结。这是硬性前提。

**风险 2 · 所有账号密码都是 `123456`（严重）**

包括财务、行政管理在内的全部账号。这是演示环境设定。

> 处置：上线前全部改为强密码，并开启首次登录强制改密（`mustChangePassword` 字段已有，需接入流程）。

**风险 3 · IP 限流阈值形同虚设（中）**

`LOGIN_MAX_PER_IP = 3000`（次/分钟）。正常访问不会触发，攻击也不会触发。真正起作用的是按用户名的 10 次/分钟锁定。

> 处置：调整到 100 以内。当时设 3000 是为了不影响开发调试。

**风险 4 · 数据库管理员可绕过全部应用层保护（中）**

工资数据存在 PostgreSQL，有库权限的人可以直接 `UPDATE` 改金额，绕过锁定保护，且不产生审计记录。

> 处置：需要数据库层审计（如 pgaudit）、最小权限的数据库账号，或独立的对账机制。应用层无法解决。

**风险 5 · 无 CSP 响应头，未做 XSS 专项审计（中）**

Token 存在 localStorage（非 cookie，因此传统 CSRF 攻击打不到），但如果前端存在 XSS 漏洞，token 可被读取。前端在渲染处使用了 `escapeHtml` 转义，但**未做过完整的 XSS 审计**。

> 处置：加 Content-Security-Policy 响应头；对所有用户可控输入的渲染路径做一次专项审计。

### 3.4 数据篡改可能性 —— 分三层结论

| 层次 | 结论 |
| --- | --- |
| **应用层** | 越权改不了（实测 10 项全部拦截）；已锁定工资改不了；操作有审计留痕 |
| **传输层** | **当前有风险** —— 无 HTTPS，同网段可嗅探、可中间人 |
| **存储层** | **有风险** —— 数据库权限持有者可任意修改且不留痕 |

对学校内网环境，最现实的威胁是**弱口令**和**明文传输**这两条，均属上线前必须解决。

## 附：审计复现方法

本文 3.1 节的十项测试可按下述方式复现（服务需运行在 `127.0.0.1:4173`）：

```bash
# 1. 不带 token
curl -s "http://127.0.0.1:4173/api/teachers/T0001/payroll?month=2026-08"

# 3. 老师账号读他人工资
TOKEN=$(curl -s -X POST http://127.0.0.1:4173/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"teacher0003","password":"123456"}' | grep -o '"token":"[^"]*' | cut -d'"' -f4)
curl -s -H "Authorization: Bearer $TOKEN" \
  "http://127.0.0.1:4173/api/teachers/T0001/payroll?month=2026-08"

# 8. SQL 注入
curl -s -H "Authorization: Bearer $TOKEN" \
  "http://127.0.0.1:4173/api/teachers?search=%27%20OR%201%3D1--"
```

跨学部隔离的完整审计已固化为自动化测试：

```bash
npm run test:finance-isolation
```

该测试以四个财务账号的身份遍历 12 个接口，在原始响应体中搜索他部关键词，共 48 次校验。
