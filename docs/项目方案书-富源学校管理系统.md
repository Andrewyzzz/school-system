## 1. 项目需求理解及范围分析报告

### 1.1 客户与业务背景

深圳市富源学校为覆盖小学、初中、高中（含幼儿园、后勤体系）的大型民办学校，教职员工总规模约 1500 人，其中任课教师约 1000 人。学校当前的排课、考勤、课时统计与薪资核算依赖人工表格，存在四类核心痛点：

1. **排课难**：多学部多年级并行，教师跨年级任课、教室共享，人工排课冲突频发、调课牵一发动全身；
2. **考勤虚**：课时签到无客观凭证，代签、补记无法防范，工资争议缺乏证据；
3. **算薪繁**：教师课时薪资与全员岗位薪资口径多、公式杂，财务每月手工核算工作量大且易错；
4. **人事散**：入职/调岗/离职流程线下流转，人事状态与排课、计薪脱节（离职老师还在课表上、停用人员还在发工资）。

### 1.2 需求理解：一条业务主线

我们把全部需求理解为一条因果链：

> **人（人事管控）→ 课（排课）→ 出勤（考勤）→ 钱（薪资）**，每一环的状态变化都必须自动、可审计地传导到下一环。

由此推导出系统的三个核心设计判断：

- **联动矩阵是灵魂**：人事状态（在职/试用/调岗中/离职中/已离职/停用）× 系统行为（能否登录/进任课池/被排课/签到/计薪）必须有唯一的规则入口，杜绝"两套系统各说各话"；
- **每一分钱可追溯**：任何工资数字都能下钻到课次、打卡流水、审批单和规则版本，争议时可导出完整证据链；
- **学期是一等公民**：学校按学期运转，系统必须支持学期接续、归档只读、跨学期数据隔离，多学部多年级并行不混乱。

### 1.3 范围分析

#### 1.3.1 范围内（按四阶段递进）

| 阶段 | 范围 | 状态 |
| --- | --- | --- |
| 一 | 任课教师闭环：多学部排课（约束求解）、教室动态码扫码签到、课时工作量确认、教师薪资生成/确认/复核/锁定/导出、调课与全局冲突校验 | **已完成** |
| 二 | 人事管控：组织架构与岗位、全员档案（敏感字段加密）、入职/调岗/离职三大审批流、人事状态联动排课与计薪、字段级审计 | **已完成** |
| 三 | 全员薪资与 OA：全员移动考勤、八类岗位工资方案引擎、请假/加班/补卡/调课 OA 审批、考勤扣款联动、津贴评审/报销/全员报表 | 规划就绪 |
| 四 | 体验终版打磨：乐观更新与撤销、移动端 PWA、动效与抽屉、快捷键、可访问性、实时协同扩展 | 规划就绪 |

#### 1.3.2 明确不在范围（及理由）

| 项 | 理由 |
| --- | --- |
| 人脸识别 / 硬件闸机对接 | 涉及生物特征合规与硬件采购，有明确需求再单独立项 |
| 银行代发直连 | 仅生成银行报盘 CSV，打款动作保留在银行渠道，规避资金安全责任边界 |

| 原生 App | PWA 覆盖"桌面图标 + 全屏"诉求，成本收益比更优 |

| 指标 | 取值 | 依据 |

## 3. 核心业务流程及规则初步方案

以下流程均已在现有系统中实现（一、二阶段）或在 PRD 中定义（三阶段），此处为提案级摘要。

### 3.1 排课流程（已实现）

```
课程规则配置 → 任课关系配置（支持自动分配空缺）→ 排课预检（容量/约束核查）
→ 约束求解（OR-Tools CP-SAT，异步任务）→ 草稿课表 → 全局冲突校验 → 发布
→ 教师端课表可见 → 调课（同一冲突校验引擎）
```

关键规则：
- **全局冲突校验**跨学部生效：同一教师、同一教室在任何年级的课位互斥；外部教师/共享教室计入全局负载；
- 求解器不可用时自动回退启发式算法并在健康检查中显式暴露（不静默降级）；
- 已归档学期的课表、调课、工资操作全部只读。

### 3.2 扫码签到规则（已实现）

- 教室大屏展示**动态二维码**（短周期轮换，防拍照转发）；教师手机摄像头扫码，无手动输入通道；
- 校验链：码有效期 → 教室匹配 → 课次匹配 → 时间窗口 → 幂等（重复扫不产生重复记录）；
- 异常场景（错教室、过期码、重复扫、非本人课次）逐一拦截并提示；签到记录构成课时计薪的客观依据。

### 3.3 教师薪资流程（已实现）

```
月度工资生成（按签到课次+方案规则）→ 教师端确认（异议走申诉）→ 财务复核
→ 锁定（锁定后不可改，更正需留痕解锁）→ 导出 CSV
```

关键规则：工资单每一明细行携带计算依据；批量锁定只处理"教师已确认+财务已复核+无待处理异常"的工资单；锁定快照永久保留。

### 3.4 人事状态机与联动矩阵（已实现，二阶段核心）

七态状态机：`待入职 → 试用期 → 在职 →（调岗中）→ 在职 / →（离职中）→ 已离职`，另有 `停用`（风控冻结）。

联动矩阵（唯一入口 `teacherEligibility`，任何模块不得绕过）：

| 状态 | 登录 | 任课池 | 已排课表 | 签到 | 计薪 |
| --- | --- | --- | --- | --- | --- |
| 试用期/在职 | ✔ | ✔ | ✔ | ✔ | ✔ |
| 调岗中 | ✔ | 原学部保留 | ✔ | ✔ | ✔ |
| 离职中 | ✔ | ✖ 不进新排课 | 生效日前保留 | ✔ | ✔（至生效日折算） |
| 已离职 | ✖ | ✖ | 生效日后自动取消 | ✖ | ✖ |
| 停用 | ✖ | 冻结 | 冻结 | ✖ | ✖（生成即拦截） |

### 3.5 审批流（已实现三类 + 三阶段扩展）

- 已实现：入职（学部发起→人事补全→总校终审→自动建档开号）、调岗（双学部确认→终审→生效日切换+课表移交清单）、离职（审批→交接清单→生效执行）、档案变更申请（本人发起→人事审核）；
- 规则：拒绝必须填原因；停留超 3 个工作日自动提醒；全程可撤回（终审前）；每一步留痕含操作人/时间/IP；
- 三阶段在同构数据结构上扩展为通用 OA 引擎（请假/加班/补卡/调课，支持会签/或签、按组织架构找审批人）。

### 3.6 考勤扣款规则（三阶段方案）

扣款不直接入账：**预扣清单 → 员工可见 → 3 天申诉期（走 OA）→ 入工资**；已批假期覆盖的异常不扣款；每笔扣款在工资单列示"哪天、什么异常、什么规则版本、多少钱"。

## 4. 系统总体解决方案及技术架构

### 4.1 总体架构

```
┌─────────────────────────────────────────────────────────┐
│  接入层  Nginx（HTTPS 终结 / 反向代理 / 静态缓存）           │
├─────────────────────────────────────────────────────────┤
│  应用层  Node.js 22 单进程服务（server/server.js）          │
│   ├─ REST API（/api/*，按域命名空间）                       │
│   ├─ SSE 实时推送（/api/events：待办/通知即时更新）           │
│   ├─ 静态前端托管（单页应用，无构建链）                       │
│   ├─ 领域模块：scheduling / attendance / payroll / hr      │
│   ├─ 异步任务框架（排课求解、批量结算）                       │
│   └─ 定时任务（审批超时扫描等）                              │
├─────────────────────────────────────────────────────────┤
│  算法层  Python + OR-Tools CP-SAT 约束求解器（子进程调用）    │
│         └─ 不可用时自动回退 JS 启发式，健康检查显式暴露        │
├─────────────────────────────────────────────────────────┤
│  数据层  PostgreSQL 16（DB_DRIVER=json|dual|postgres 三态）  │
│   ├─ 影子快照差量持久化（只写变更，原子提交）                  │
│   ├─ PII 加密存储（AES-256-GCM，密钥环境变量注入）            │
│   └─ JSON 文件模式保留（小规模/回滚底）                       │
└─────────────────────────────────────────────────────────┘
  终端：桌面浏览器 / 手机浏览器（响应式+PWA 规划）/ 教室大屏页
```

### 4.2 关键技术选型与理由

| 选型 | 理由 |
| --- | --- |
| Node.js 22 原生 HTTP（零 Web 框架） | 依赖面最小=供应链风险最小=十年可维护；单校规模无需微服务复杂度 |
| 单文件无框架前端 | 无构建链、无 npm 前端依赖树，任何浏览器直接运行；改版只需替换静态文件+缓存版本号 |
| PostgreSQL 16 | 成熟开源、零许可费；事务与备份体系完善；`json→dual→postgres` 三态驱动支持不停机演进 |
| OR-Tools CP-SAT | Google 开源约束求解器，千级课位分钟内可行解，远优于手写启发式 |
| SSE（而非 WebSocket） | 单向推送场景足够、HTTP 语义天然穿透代理、实现与运维成本低 |
| 全部开源栈 | 无任何商业许可依赖，学校长期持有成本为零（见第 12 章） |

### 4.3 实测性能（可复验）

| 场景 | 结果 | 复验方式 |
| --- | --- | --- |
| 3000 虚拟用户混合负载 | 稳态 ~400-448 req/s，业务接口 P95 ≤ 35ms，P99 ≤ 131ms，0 错误 | `scripts/load-test.js` |
| 登录风暴（口令校验高峰） | 异步 pbkdf2 + 线程池，P50 从 2.2s 优化至毫秒级 | 同上 |
| 排课求解 | 16 班 133 节课位规模，CP-SAT 秒级~30 秒出解 | `npm run test:benchmark` |
| 服务重启数据存活 | PostgreSQL 驱动下会话与业务数据完整存活 | E2E 记录 |

### 4.4 可靠性设计

- 存储写入：写合并 + 原子落盘（tmp+rename）/事务提交，杜绝半写状态；
- 进程守护：systemd `Restart=always`，崩溃自动拉起；
- 健康体系：`/api/health`（分钟级监控）+ `/api/phase1/readiness`（部署级自检，含求解器/加密密钥/数据库连接/回填完整性等检查组）；
- 备份：PostgreSQL 每日全量 + WAL 归档，保留 90 天，每月恢复演练；JSON 阶段滚动 50 份快照。

## 11. 信息安全和个人信息保护方案

### 11.1 数据分级与加密

| 级别 | 数据 | 措施 |
| --- | --- | --- |
| 敏感个人信息 | 身份证号、银行卡号 | **AES-256-GCM 加密落库**，页面仅显示掩码；查看完整值需填写原因，每次查看记入审计（含操作人/时间/IP）；密钥经环境变量注入，不落代码库，离线备份两份（Q5） |
| 一般个人信息 | 姓名、电话、紧急联系人 | 访问控制 + 变更走审批/留痕 |
| 薪资数据 | 工资金额、方案 | 仅财务与总校可见；人事、主管、学部负责人在任何界面/接口不可见金额（含服务端裁剪，自动化越权测试保障） |
| 口令 | 登录密码 | pbkdf2 加盐哈希；默认密码首登强制修改；重置留痕 |

### 11.2 访问控制

- 七角色权限矩阵（`docs/roles-and-permissions.md`）：一角色一条主职责线，职责分离红线（管档案者不见薪资、审批链不可自审自批）；
- 学部负责人 scope 过滤：跨学部访问服务端 403（有自动化测试断言）；
- 会话管理：令牌哈希存储、过期回收、账号停用即时踢出。

### 11.3 攻击面控制

- 登录保护：按用户名失败计数锁定 + 单 IP 高上限限速（NAT 友好）、异步口令校验抗登录风暴；
- 输入防护：请求体 5MB 上限、CSV 注入转义（`=+-@` 前缀）、全站输出 HTML 转义；
- 传输安全：生产强制 HTTPS（扫码功能天然要求）；
- 供应链：后端零 Web 框架、前端零构建依赖，第三方依赖面极小（pg、ortools 等个位数）。

### 11.4 审计与可追溯

- 人事全字段级审计：任何档案变更记录前值/后值/操作人/原因（敏感字段 diff 只存掩码）；审计日志只增不删，无删改接口；
- 打卡流水只增不改，纠错走补卡审批；工资锁定快照永久保留；
- 制度争议时可导出完整证据链：申请 → 审批 → 原始记录 → 规则版本。

### 11.5 个人信息保护合规要点

- 最小必要：只采集业务必需字段；定位打卡（若 Q7 选定位方案）仅采集打卡瞬时坐标、端上明示告知并记录首次知情同意、坐标保留 ≤12 个月自动清理；
- 员工权利：本人档案可查、联系方式变更自助申请、工资单本人可见可申诉；
- 数据出境：系统与数据全部部署于境内学校自有/租用服务器，无出境场景；
- 留存与销毁：备份保留 90 天；离职人员档案按学校制度留存，销毁操作需授权并留痕。

## 14. 源代码、知识产权及项目退出方案

### 14.1 源代码交付

- 交付**全部源代码**（后端/前端/求解器/测试/脚本/文档），以 Git 仓库形式移交，含完整提交历史；
- 无任何加密、混淆、授权锁、远程许可校验；学校可在自有环境独立构建运行（`npm install` + 文档步骤即可）；
- 每阶段验收即同步移交该阶段代码，不存在"尾款前扣代码"。

### 14.2 知识产权安排

- 本项目为学校定制开发，**交付物的知识产权归属按合同约定**（建议：定制代码著作权归学校，或归学校+开发方共有并授予学校永久免费使用/修改/委托第三方维护的权利——两案任选，合同定稿）；
- 所依赖第三方组件均为宽松开源许可（MIT/Apache-2.0 等），清单随代码交付，无传染性许可（GPL）核心依赖，学校商用无风险；
- 开发方保留通用技术方法（非学校业务数据/业务规则）的复用权。

### 14.3 项目退出方案（无论何种原因终止合作，学校不被绑架）

退出交接清单（承诺在退出决定后 30 日内完成）：

1. **代码**：最终版仓库 + 全部分支/标签/提交历史移交；
2. **数据**：PostgreSQL 全量导出（标准 pg_dump，任何团队可接手）+ 全部 CSV 导出口径说明；
3. **密钥与凭证**：加密密钥、服务器凭证、域名/证书控制权全部移交并轮换；
4. **文档**：部署手册、运维 Runbook、四阶段 PRD/TODO、数据字典（表结构 SQL 即文档）；
5. **交接支持**：为接手方提供 **[N 留白]** 小时技术答疑；
6. **数据销毁**：开发方本地副本按学校要求销毁并出具书面确认。

技术层面的退出友好性是架构决定的：全开源栈 + 极小依赖面 + 标准 PostgreSQL + 完整文档，任何具备 Node/SQL 能力的团队可接手维护。

## 15. 质保和长期运维服务方案

### 15.1 质保期

- 每阶段验收通过之日起 **[N 个月留白]** 质保期：质保范围内缺陷（与验收基线不符的功能问题）免费修复；
- 质保不覆盖：学校自行修改代码引发的问题、超出验收范围的新需求（走变更流程）、基础设施故障（服务器/网络）。

### 15.2 故障响应分级（SLA）

| 级别 | 定义 | 响应 | 恢复目标 |
| --- | --- | --- | --- |
| P0 | 系统不可用 / 数据丢失风险 / 工资错算 | 30 分钟 | 4 小时（含回滚手段） |
| P1 | 核心流程受阻（无法排课/签到/结算），有临时绕行 | 2 小时 | 1 个工作日 |
| P2 | 非核心功能异常 | 1 个工作日 | 下一维护窗口 |
| P3 | 体验问题 / 咨询 | 2 个工作日 | 排期处理 |

**敏感时段加强**：每月结算周（工资生成→锁定）与开学排课周为加强保障期，P0/P1 响应时间减半。

### 15.3 日常运维内容（长期服务包，费用见第 13 章留白）

| 项 | 频率 | 内容 |
| --- | --- | --- |
| 健康监控 | 分钟级自动 | `/api/health` 告警（状态/存储/求解器/数据库连接） |
| readiness 巡检 | 每日 | 部署自检全项核对，FAIL 当日处理 |
| 备份与演练 | 每日备份 / 每月演练 | PostgreSQL 全量+WAL，恢复演练留记录 |
| 安全维护 | 每季度 | 依赖安全更新、密钥备份核对、账号权限复审 |
| 版本更新 | 按需 | 走 `docs/system-update-process.md` 流程：变更→回归→灰度→记录 |
| 制度规则维护 | 按学校通知 | 工资方案/扣款规则调整（版本化生效，不改已结算月份） |
| 培训 | 每学期 1 次 + 新角色按需 | 面向新入职管理人员的角色操作培训 |

### 15.4 运维交接与升级承诺

- 运维期内所有变更进 CHANGELOG（内容/验证/回滚方式），学校可完整审计；
- 每年提供一次系统健康年报（性能趋势、容量评估、风险清单、升级建议）；
- 长期演进（如多校区、多实例）按第 4 章架构预留路径评估，不推倒重来。
